# Introduction {#sec:intro}

The open `SKILL.md` specification has rapidly transformed how Large Language Model (LLM) coding agents acquire reusable procedures, packaging natural-language instructions, helper scripts, and reference templates into filesystem folders loaded on demand [@destefanis2026gitskills; @xu2026agentskills]. Yet empirical audits of this ecosystem reveal severe engineering fragility. Mining over 3.79 million public `SKILL.md` files across 282,200 GitHub repositories, @destefanis2026gitskills observe that natural-language skills lack compilers, type checkers, or centralized package verifiers. Across 138,133 public skills, @zhang2026reusable find that 91.8% contain at least one defect—dominated by bloated instruction bodies, broken metadata, and disorganized resources—while SkillsBench [@li2026skillsbench] demonstrates across 87 tasks and 18 model-harness configurations that curated, focused skills (at most three modules) lift task pass rates by 16.6 percentage points (from 33.9% to 50.5%), whereas exhaustive documentation bundles degrade performance. Simultaneously, security evaluations expose high vulnerability rates across community registries [@xu2026agentskills; @badhe2026skillsecurity], up to 80% attack success rates on skill-file prompt injections [@schmotz2026skillinject], and semantic supply-chain hijacking of skill discovery and governance [@saha2026underhood].

Academic research and paper authoring stress every weakness of current Agent Skill designs at once. A full research lifecycle spans literature discovery, experimental design, reproducible script execution, visualization, manuscript drafting, peer review, and double-blind LaTeX compilation. Existing automated scientific writers—such as The AI Scientist [@lu2024aiscientist], The AI Scientist-v2 [@yamada2025aiscientistv2], CycleResearcher [@weng2024cycleresearcher], and PaperOrchestra [@song2026paperorchestra]—operate as standalone applications coupled to external LLM API keys or fixed GPU inference pipelines. Even when decoupled from experiment execution, as in PaperOrchestra [@song2026paperorchestra], monolithic drafting pipelines face four unresolved failure modes when ported to interactive coding-agent harnesses:

1. **Context bloat and harness lock-in:** Loading an entire multi-stage research workflow into one monolithic skill exceeds host loader ceilings, wastes prompt tokens on inactive stages, and prevents portability across Antigravity, Claude Code / Cowork, and Codex.
2. **Silent provenance and conversion drift:** Without deterministic checks binding manuscript numbers to canonical non-synthetic run logs and citations to saved primary-source snapshots, drafting and Markdown-to-LaTeX conversion silently introduce fabricated decimals, synthetic dry-run leakage, unverified references, or dropped equations and labels.
3. **Intrinsic self-review bias:** As @huang2024selfcorrect demonstrate, LLMs cannot reliably self-correct reasoning in the same generation context without external feedback. Asking the drafting session to review its own paper fails to catch missing ablations, claim-vs-source contradictions, or subtle anonymity leaks.
4. **Scientific supply-chain attack surfaces:** Scientific authoring uniquely consumes untrusted external data—scraped paper abstracts, user PDFs, and third-party conference LaTeX archives—exposing agents to indirect prompt injection [@greshake2023indirect], Zip Slip archive traversal, LaTeX `\write18` or `\input{|...}` shell pipes, arbitrary `\openin`/`\openout` filesystem access, and double-blind metadata leakage in compiled PDFs.

To address these challenges, we design and evaluate **PaperOEGM** (Paper Orchestra + Elephant-Goldfish Model), a composable, zero-API-key Agent Skills plugin spanning Antigravity, Claude Code / Cowork, and Codex. PaperOEGM runs exclusively on the user's active coding-agent runtime with zero external LLM API keys and zero third-party Python package installations. Its core architectural principle is a strict separation of concerns between *deterministic mechanical verification* and *fresh-context semantic critique*, illustrated in Figure~\ref{fig:architecture}.

![PaperOEGM three-layer architecture: progressive-disclosure skills with human checkpoint gates (Layer 1), zero-dependency stdlib verifier backbone (Layer 2), and flat 1-level read-only critics paired with paranoid LaTeX sandboxing and deterministic multi-harness packaging (Layer 3).](../visuals/assets/fig_architecture.pdf){#fig:architecture width=0.98\textwidth}

PaperOEGM organizes the workflow into ten chronological progressive-disclosure skills (`po-start` through `po-format`), each capped under 12,000 bytes with `disable-model-invocation: true` so the host agent never triggers destructive or premature transitions autonomously. Shared state lives in a single authoritative `paper_state.json` tracked by a zero-dependency Python 3.10+ standard-library CLI (`po_tools.py`), which audits SHA-256 input-digest drift, verifies BibTeX-to-ledger-to-snapshot parity, validates inline `<!-- run:<run_id> -->` numeric blocks against canonical non-synthetic `metrics.json`, checks `.md`-to-`.tex` conversion parity, scans archives for Zip Slip and TeX shell pipes, and enforces double-blind hygiene. Mechanical checks alone cannot catch semantic flaws such as citation distortion or integer-only falsification; PaperOEGM therefore pairs `po_tools.py` with five stateless, read-only critic subagents dispatched *flat at depth one* in parallel (avoiding nested synthesizer topologies that fail on non-nesting runtimes), bounded to 1,500 output tokens each and verified via pre/post SHA-256 snapshots (`check-readonly`).

This paper makes four empirical and engineering contributions:

* **Modular zero-API-key multi-harness skill architecture (Section~\ref{sec:method}):** We formalize a 10-skill progressive-disclosure graph, single-source state schema, safe offline experiment runner contract (`--dry-run` isolation, atomic `metrics.json`, `EXIT` traps), flat 1-level read-only critic topology, paranoid LaTeX build wrapper, and deterministic ZIP packager across Antigravity, Claude Code, and Codex.
* **PO-FaultBench and deterministic boundary analysis (Section~\ref{sec:experiments}):** We construct a 120-workspace fault-injection corpus (8 fault families plus 40 hard negative controls) alongside a 20-case adversarial evasion suite across five seeds (700 live CLI runs). `po_tools.py` achieves 100.0% recall and 0.0% false-positive rate (FPR) on mechanical faults in 115.72 ms/workspace, outperforming Compiler-Only (6.25% recall) and No-Inline-Provenance ablations (87.5% recall), while dropping to 0.0% recall on semantic and obfuscated-macro evasions—empirically delineating the boundary where native TeX sandboxing and semantic critics are indispensable.
* **Packaging context economics and scalability (Section~\ref{sec:experiments}):** PaperOEGM reduces median active-stage prompt context by 82.16% (97.14% startup index reduction) relative to a monolithic baseline, maintains 81.14% headroom below Antigravity's 24 KB limit (where a reference multi-harness plugin [@google2026egm] reaches 24,257 bytes), passes `claude plugin validate` with zero defects, and achieves 100.0% deterministic ZIP SHA-256 parity. Across 20 to 120 citations and 5 to 30 runs, all four verifier subcommands complete in 260.37 ms to 272.48 ms, offload 87.96% of citation metadata from critic context, and compile three double-blind venues (`acmart[sigplan]`, `cvpr2025`, `iclr2025`) with zero identity leaks.
* **Live hybrid fresh-context critic evaluation (Section~\ref{sec:experiments}):** Across three distinct seeded domain manuscripts containing 30 planted flaws (15 mechanical, 15 semantic), deterministic verification recovers 100.0% of mechanical flaws but 0.0% of semantic flaws (50.0% total), whereas 15 live flat-parallel read-only critic invocations recover 100.0% of planted semantic flaws (lifting hybrid recall to 100.0%) with 0.0 clean-control false positives, 0 workspace mutations, and peak output within the 1,500-token budget. We candidly report negative results, single-harness evaluation boundaries, and threats to validity in Section~\ref{sec:limitations}.
